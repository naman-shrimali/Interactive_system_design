Everything upstream is straightforward. The difficulty is concentrated in one place: the network call to a third party you don't control, which can fail in ways that are indistinguishable from success.

### The core problem

A worker sends an SMS. The provider accepts it and charges you. The acknowledgement is lost to a network blip. The worker sees a timeout, assumes failure, and retries — and the user gets two texts and you pay twice.

This isn't rare. At millions of messages a day, "rare" network events happen constantly. And you cannot fix it by not retrying: transient failures are common, and a system that gives up on the first timeout will silently drop a meaningful fraction of its traffic.

So retries are mandatory, and retries cause duplicates. The resolution is not to eliminate duplicates but to make them harmless.

### Idempotency keys

Every notification carries a unique key, generated by the caller at trigger time — commonly a hash of `(user, event_id, channel)`.

Before sending, the worker checks whether that key has already been processed. If so, it's a no-op. Two workers processing the same message concurrently will race on that check, so the store must make it atomic: a conditional insert that fails if the key exists, not a read followed by a write.

Better still, **push the key to the provider**. Most transactional providers accept an idempotency key and will deduplicate on their side, which closes the window your own check can't — the gap between "provider accepted" and "we recorded that it accepted".

Between your check and theirs, duplicates become rare enough to stop worrying about. Exactly-once is unachievable across a network boundary; this is how you get the observable behaviour without the impossible guarantee.

### Retries that don't make things worse

Naive retry logic turns a provider hiccup into a self-inflicted outage. Three rules:

**Exponential backoff with jitter.** Retry after 1s, 2s, 4s, 8s — and add randomness. Without jitter, everything that failed during a 30-second provider blip retries in the same instant afterwards, hammering a recovering service. Jitter is the difference between a smooth recovery and a second outage.

**Only retry what's retryable.** A 500 or a timeout is worth retrying. A 400 "invalid phone number" will fail identically forever, and retrying it wastes capacity and delays real work. Classify provider errors into retryable and permanent, and fail permanent ones immediately.

**Bound the attempts.** After a handful of tries, stop.

### Dead-letter queues

Messages that exhaust their retries go to a dead-letter queue rather than being dropped or retried forever.

This does two things. It keeps a permanently-failing message from blocking the queue behind it — the classic poison-message problem, where one malformed payload stalls a worker pool indefinitely. And it preserves the message for inspection, so you can find out *why* it failed and replay it after a fix.

A growing DLQ is one of the more useful alerts in this system: it means something systemic is broken, and it tells you exactly which messages were affected.

### Circuit breakers

When a provider is comprehensively down, continuing to send is worse than useless — every request consumes a worker for the duration of a timeout, and your worker pool fills with calls that are all going to fail. Throughput for *other* providers suffers because workers are tied up.

A circuit breaker watches the failure rate and, past a threshold, stops calling the provider entirely for a cooling-off period, failing fast instead. Periodically it lets one request through to test recovery. This converts "every worker blocked on a 30-second timeout" into "fail immediately, queue drains to DLQ or waits", which is far easier to reason about and recover from.

### Knowing what happened

A notification tracking table records, per notification: the idempotency key, channel, current state (queued / sent / delivered / failed / suppressed), attempt count, provider message ID, and timestamps.

That table answers the question every support ticket asks — "did the user get it?" — and the provider message ID is what lets you escalate to the provider with something specific.

Worth monitoring:

- **Queue depth per channel** — the earliest signal that a provider is degrading.
- **Send failure rate per provider** — distinguishes your bug from their outage.
- **DLQ growth** — systemic failure.
- **Suppressed counts by reason** — a spike in opt-out suppression usually means someone triggered a campaign at the wrong audience.
- **Time from trigger to send**, especially for transactional messages where the user is waiting.

### Ordering

Don't promise it. Notifications are independent events, they traverse different channels with different latencies, and providers make no ordering guarantees. If two notifications genuinely must arrive in order, the correct fix is usually to send one message containing both facts.
