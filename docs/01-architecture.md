# 01 — High-Level Architecture & Tech Stack

## Architecture at a glance

```
┌────────────────────────────┐        ┌──────────────────────────────┐
│  client/  (React + Vite)   │  HTTP  │  server/  (Express + TS)     │
│  - curriculum browser      │ ─────▶ │  - REST API  /api/*          │
│  - markdown reader         │  JSON  │  - better-sqlite3            │
│  - React Flow diagrams     │        │  - serves data/app.db        │
│  - notes & progress UI     │        └──────────────┬───────────────┘
└────────────────────────────┘                       │
                                          ┌──────────▼───────────┐
   scripts/ (run at build/authoring time) │  data/app.db (SQLite)│
   - ingest primer markdown → content/    └──────────▲───────────┘
   - validate diagram JSON                           │
   - seed content/*.json  ───────────────────────────┘
```

Three independent parts. The **scripts** pipeline turns source material into `content/*.json`; the **server** seeds those files into SQLite and exposes a REST API; the **client** is a pure consumer of that API.

## Tech stack (all open-source)

| Layer | Choice | License | Why (esp. for small AI coder models) |
|---|---|---|---|
| Frontend framework | React 18 + TypeScript + Vite | MIT | Most-represented stack in training data; fewest hallucinated APIs |
| Styling | Tailwind CSS v3 | MIT | Utility classes keep styling inside JSX — no cross-file CSS coupling for a small model to break |
| Client state | Zustand | MIT | One store file, no boilerplate, no context wiring mistakes |
| Routing | React Router v6 | MIT | Standard |
| Markdown render | react-markdown + remark-gfm | MIT | Renders primer content incl. tables safely (no `dangerouslySetInnerHTML`) |
| Diagrams | **React Flow (`@xyflow/react` v12)** | MIT | See [docs/04-diagrams.md](04-diagrams.md) for full evaluation |
| Icons | lucide-react | ISC | Ready-made server/database/cloud icons → no hand-drawn SVG tasks |
| Backend | Node 20 + Express 4 + TypeScript | MIT | Simplest possible REST layer; hugely familiar to all models |
| Validation | zod | MIT | Runtime request-body validation with TS inference |
| Database | SQLite via better-sqlite3 | MIT | Local single-user app: zero config, synchronous API (no async/await bugs), plain SQL — schemas in docs are copied verbatim |
| Diagram schema validation | ajv | MIT | Validates hand-authored diagram JSON against our JSON Schema |

**Deliberate exclusions:** no ORM (Prisma/Drizzle add a schema-indirection layer where small models drift from the documented DDL), no monorepo tooling (client and server are two plain npm packages), no auth (local single user), no CSS-in-JS.

## API surface (summary — exact contracts in docs/02)

| Method + path | Purpose |
|---|---|
| `GET /api/health` | liveness check |
| `GET /api/curriculum` | full tree: sources → chapters → sections (+ per-section progress rollup) |
| `GET /api/sections/:id` | one section: markdown, external links (+completion), diagram list (+viewed) |
| `GET /api/diagrams/:id` | one diagram spec JSON |
| `PUT /api/progress/section/:id` | set section status |
| `PUT /api/progress/link/:id` | set external-link completed flag |
| `PUT /api/progress/diagram/:id` | mark diagram viewed |
| `GET /api/progress/summary` | totals per chapter/source for the dashboard |
| `GET/POST /api/notes`, `PUT/DELETE /api/notes/:id` | notes CRUD (anchored to chapter OR section) |

Server runs on **port 4000**; Vite dev server on **5173** proxies `/api` → `http://localhost:4000` (configured in `vite.config.ts`), so the client code always calls relative `/api/...` paths.
